# Agent 評估中的基礎設施噪聲

你升級了模型。你的 SWE-bench 分數跳漲了兩分。值得慶祝嗎？

也許。又也許，你只是給評估容器多分配了一個 CPU 核心。

Anthropic 工程團隊最近的工作為 Harness 構建者長期以來的猜測提供了硬資料：**基礎設施配置可以使 Agent 基準測試分數波動高達 6 個百分點**——這往往超過了公開排行榜上頂級模型之間的差距。這一發現應該改變每個評估團隊對 Harness 配置的思考方式。

本指南拆解了這個問題，梳理了資料，並提供了配置評估環境的具體建議，以確保衡量的是模型能力而非基礎設施運氣。

---

## 為什麼 Agent 評估不是靜態基準測試

傳統基準測試——MMLU、HumanEval、HellaSwag——本質上是一次函式呼叫。你傳送一個提示，得到一個補全，然後評分。計算環境幾乎無關緊要。2 核虛擬機器和 64 核工作站產出的分數完全相同，因為模型的推理由遠端 API 處理，本地機器只負責編排 I/O。

Agent 評估徹底打破了這個假設。

當一個 Agent 處理 SWE-bench 任務時，它不僅僅是生成一個補丁。它：

- **派生程序** — 程式碼檢查器、測試執行器、構建工具，有時是多個並行。
- **讀寫檔案** — 在大型程式碼倉庫中導航，搜尋數千行程式碼。
- **迭代** — 執行測試、閱讀失敗資訊、編輯程式碼、再執行測試。
- **管理時間** — 決定何時放棄某個策略並嘗試其他方案。

這些步驟中的每一步都依賴執行時環境。在高效能機器上 8 秒完成的測試套件，在受限容器上可能需要 90 秒。一個在 5 分鐘壁鐘時間後被終止的 Agent 解決的問題會比被允許執行 30 分鐘的少——不是因為模型更差，而是因為時間用完了。

**執行時環境是測試的一部分。** 這是根本區別。在靜態基準測試中，基礎設施是背景管道。在 Agent 評估中，基礎設施是一個實驗變數。

## 資源限制執行的隱藏影響

並非所有資源限制都是一樣的。兩個 Harness 都可以宣稱"4 GB 記憶體限制"，但根據*如何*執行該限制，可能產出截然不同的分數。

### 保證分配 vs. 硬性終止

考慮兩種執行策略：

| 策略 | 達到 4 GB 時的行為 |
|------|-------------------|
| **保證分配** | 容器*保證*獲得 4 GB。在主機有餘量時可能偶爾超過。程序在記憶體壓力下會變慢但繼續執行。 |
| **硬性終止閾值** | 容器一碰到 4 GB，OOM killer 就會觸發。Agent 的程序樹全部死亡。任務失敗。 |

名義上相同的限制。結果大不相同。

在保證分配下，一個執行測試套件時短暫飆升到 4.2 GB 的 Agent 能存活——主機吸收了這次突發，測試完成，Agent 讀取輸出並繼續。在硬性終止下，同樣的飆升就是一次任務失敗。Agent 永遠沒機會恢復。

### CPU：份額 vs. 固定

CPU 存在類似的分歧：

- **CPU 份額**（如 Docker `--cpu-shares`）提供按比例的訪問。如果主機空閒，你的容器想用多少核就用多少。如果主機負載高，你獲得公平份額。分數變得取決於機器上*還有什麼*在執行。
- **CPU 固定**（如 `--cpuset-cpus=0-3`）分配特定核心。確定性強，但如果 Agent 的負載是突發性的則比較浪費。

如果你的評估叢集使用 CPU 份額並在同一主機上並行執行多個評估，你就引入了任務之間的隱藏關聯。Agent A 的分數取決於 Agent B 是否恰好在同一時間執行編譯任務。

### 時間限制：壁鐘時間 vs. CPU 時間

大多數 Harness 對每個任務施加壁鐘時間超時。但壁鐘時間是模型能力*和*基礎設施速度的聯合函式。

一個生成了高效計劃但執行在慢機器上的 Agent 可能會超時。同樣的 Agent 在更快的硬體上還剩幾分鐘就完成了。模型沒變。分數變了。

這就是為什麼基礎設施配置不是腳註。**它是一等實驗變數。**

## 資料：擴展資源時會發生什麼

Anthropic 的團隊進行了一項對照實驗：使用同一個模型、同一個 Agent 腳手架、同一組任務，只改變基礎設施分配。他們測試了三個層級：

- **1x** — 受限基準（代表最小 CI 配置）。
- **3x** — 基準的三倍 CPU 和記憶體。
- **無上限** — 無人工資源限制。

結果清晰地分為兩個區間。

### 1x → 3x：消除基礎設施錯誤

將資源從基準擴大三倍主要**減少了基礎設施引發的失敗**。基礎設施錯誤率從約 5.8% 降至 2.1%。

這些是 Agent 的方法方向正確，但環境殺死了它的任務——OOM、超時、磁碟滿。在 3x 下，這些失敗模式基本消失。

關鍵是，1x 和 3x 之間的整體基準分數變化**在正常的執行間方差範圍內**。換句話說，分數差異與噪聲無法區分。

這意味著什麼？在某個資源閾值以下，配置之間（或執行之間）的分數差異主要衡量的是**基礎設施多頻繁地造成障礙**，而非模型的能力。

### 3x → 無上限：Agent 利用額外資源

完全移除資源限制則呈現了不同的故事。分數**顯著**上升——遠超噪聲水平線。

在資源不受限時，Agent 表現出質的不同行為：

- **更激進的探索。** Agent 執行更大的測試套件，並行嘗試更多修復策略，在放棄前迭代更多次。
- **更重度的 Tool 使用。** 不用擔心記憶體，Agent 可以持有更多上下文——更大的檔案讀取、更廣泛的 grep 結果、更大的 diff。
- **更長的推理鏈。** 沒有緊迫的壁鐘限制，Agent 可以承受更長時間的"思考"——嘗試一種策略，失敗，回溯，再嘗試另一種。

額外的資源不僅僅是防止了失敗。它們**通過啟用在受限預算下不可行的策略，擴展了 Agent 能解決的問題集。**

### 6 個百分點的波動

從 1x 到無上限的全範圍內，分數差異達到約 **6 個百分點**。作為參考，在近期的 SWE-bench 排行榜上，排名第 1 和第 5 的系統之間的差距通常小於此。

這意味著一個 Harness 配置選擇——可能由一個 DevOps 工程師選擇容器大小時決定——對釋出分數的影響可以超過被評估的實際模型改進。

## 對 Harness 工程的啟示

如果你正在構建或維護評估 Harness，這些資料要求你轉變對資源配置的思考方式。

### 資源配置是設計決策，不是預設值

大多數團隊將基礎設施配置視為運維細節。有人選了一個"看起來合理"的容器大小，然後再也不去重新審視。Anthropic 的發現表明，這相當於在不記錄的情況下選擇測試的難度等級。

每個資源引數——CPU 數量、記憶體上限、磁碟空間、壁鐘超時、網路頻寬——都是**評估設計空間的一個維度**。它應該：

- **記錄**在評估規範中。
- **版本控制**與任務定義和評分邏輯放在一起。
- **報告**在任何釋出的結果中。

### 低於 3x，你在衡量基礎設施

如果你的評估環境資源受限（大多數基於 CI 的配置都是如此），相當一部分任務失敗可能是基礎設施問題而非模型侷限。

在將分數下降解讀為模型退化之前，先問：

- 是否有任務因容器 OOM 而終止？
- 是否有任務觸發了壁鐘超時？
- 你是否在共享 CPU 的同一主機上執行多個評估？

如果這些問題的答案是"是"或"不知道"，你的訊雜比可能比你想像的更差。

### 比較需要完全相同的基礎設施

這聽起來顯而易見，但卻經常被違反。兩個團隊用不同的容器大小、不同的 CPU 分配和不同的超時值評估"SWE-bench"，執行的不是同一個基準測試。他們的分數不可直接比較。

如果你的 Harness 沒有固定並報告確切的基礎設施規格，**跨團隊比較是不可靠的。**

## 實用建議：配置你的評估環境

基於以上資料和原則，以下是一個具體框架，用於配置衡量你真正關心的內容的基礎設施。

### 1. 指定下限和上限

不要使用單一資源值。定義兩個：

- **下限（最低保證）：** 無論主機上還有什麼在執行，Agent 始終可用的資源。這防止基礎設施資源飢餓破壞你的結果。
- **上限（突發限制）：** Agent 在瞬時峰值期間能訪問的最大資源。這防止單個失控程序使主機不穩定。

例如：

```yaml
resources:
  cpu:
    floor: 4 cores (guaranteed)
    ceiling: 8 cores (burstable)
  memory:
    floor: 8 GB (guaranteed)
    ceiling: 16 GB (hard limit, OOM above this)
  timeout:
    per_task: 30 minutes (wall clock)
  disk:
    floor: 20 GB
```

下限確保可復現性。上限防止失控成本。兩者一起定義了評估的"基礎設施契約"。

### 2. 將下限設為最小可行配置的 3 倍

資料表明，低於最小配置的 ~3 倍時，你主要衡量的是基礎設施噪聲而非模型能力。將此作為經驗法則：

1. 找到**已知良好的 Agent 能夠完成中位數任務**且無資源錯誤的最小配置。
2. **乘以 3。** 這就是你的下限。

這不能保證零基礎設施噪聲，但將噪聲水平線推低到分數差異更可能反映真實能力差距的程度。

### 3. 單獨監控基礎設施故障

在每次評估執行中跟蹤這些指標：

- **OOM 終止次數** — 多少任務因記憶體耗盡而終止。
- **超時次數** — 多少任務觸發了壁鐘限制。
- **磁碟滿次數** — 多少任務耗盡了磁碟空間。
- **基礎設施錯誤率** —（OOM + 超時 + 磁碟滿）/ 總任務數。

將基礎設施錯誤率與基準分數一起報告。如果超過 2-3%，你的結果已被汙染。在解讀模型訊號之前先修復基礎設施。

### 4. 隔離評估執行

不要在併發評估執行之間共享主機，除非你使用硬性資源隔離（帶保證分配的 cgroups，而不僅僅是 CPU 份額）。

更好的做法：**一次評估執行，一臺機器**（或一個專用虛擬機器/Pod）。專用例項的邊際成本與除錯一個最終被證明是嘈雜鄰居導致的幻影分數退化的成本相比微不足道。

### 5. 版本控制你的基礎設施規格

將基礎設施配置新增到評估的版本控制規範中：

```
eval-spec/
├── tasks/
├── scoring/
├── scaffold/
└── infrastructure.yaml    ← 這是新的。將其視為必需項。
```

釋出結果時，包含基礎設施規格。比較執行時，先比較基礎設施規格。

### 6. 執行基礎設施敏感性檢查

定期（至少每季度一次或每次更改評估環境時），在 1x、3x 和無上限資源下運行同一模型。比較：

- 如果 1x 和 3x 分數的差異大於你的典型執行間方差，你的下限太低了。
- 如果 3x 和無上限分數相近，你的 3x 配置足以捕捉模型在此任務集上的能力。
- 如果 3x 和無上限仍然分歧，某些任務確實需要更多資源——考慮這些任務是在測試模型能力還是基礎設施容量。

## 更大的圖景

關於基礎設施噪聲的討論實際上是關於**我們在衡量什麼**的討論。

基準分數不是模型的屬性。它是一個*系統*的屬性：模型 + 腳手架 + 基礎設施 + 任務集 + 評分函式。當我們剝離基礎設施維度並假裝分數純粹關於模型時，我們在自欺欺人——並可能在做出關於哪些模型該上線的錯誤決策。

對於 Harness 工程師來說，結論很簡單：**以你對待任務定義和評分邏輯同樣的嚴謹態度對待你的基礎設施配置。** 它不是管道工程。它是實驗的一部分。
