我們在做 **Nexu**（龍蝦 🦞），一個可以一鍵安裝的 OpenClaw 桌面客戶端，開源在 GitHub 上。

產品上線後增長一直在跑。新使用者註冊時會贈送免費積分，可以用來呼叫平臺上的各種大模型。

某天做使用者資料清洗的時候，我們注意到一件事——**有一個從沒見過的郵箱域名，註冊使用者數異常地高**。超過了很多企業域名，穩居域名排行榜前列。

這篇文章完整記錄了我們從**「發現異常 → 多維度下鑽 → 建立基線 → 得出結論」**的全過程。我們還把整套排查方法做成了一個開源 Skill，文末可以直接安裝使用。做 SaaS 的朋友，尤其是帶免費額度模式的產品，可能會有共鳴。

## 01 / 一個不該出現在排行榜上的域名

按郵箱域名聚合排序，排在前面的都是常客——gmail.com、qq.com、各種公司域名。

但有一個域名卡在了很前面的位置（出於脫敏，下文統一稱為 **xx.love**）。它名下的註冊使用者超過 **1000+**。

一個從沒聽過的域名，註冊量卻比很多企業域名還高。這本身就是一個值得深挖的訊號。

簡單查了一下這個域名的背景：

- 2026 年初註冊，WHOIS 隱私保護，看不到註冊人
- DNS 託管 Cloudflare，配了 MX 記錄——**有郵件收發能力**
- 沒有 A 記錄，沒有網站，沒有 ICP 備案

一個專門用來收發郵件、但不做任何公開網站的域名。記住這個特徵，後面會用到。

## 02 / 兩個截然不同的階段

把這 1000+ 個帳號按註冊時間排開，不是均勻分佈，而是**明顯分成了兩個階段**。

**第一階段（Day 1 ~ Day 7）：小規模試探**

每天個位數到幾十個，總共約 150 個。郵箱字首風格多樣——有看起來像人名的（linlong、wuyan），有明顯手敲測試的（ooo、qwe），也有混合字串。不統一，像是在摸索。

**第二階段（Day 8 之後）：大規模放量**

單日湧入 700+，字首幾乎清一色變成了 **6 位字母數字隨機串**（如 01mh07、x9k2p3）。10 分鐘窗口裡多次出現 16~18 個帳號的密集註冊，註冊間隔中位數約 **37 秒**。

這不是規模變大了，是**命名策略發生了切換**——從"人在鍵盤前敲"變成了"指令碼在跑"。

## 03 / UA 指紋也在同步切換

如果只看註冊行為可能還不夠，但 User-Agent 的變化進一步印證了階段切換。

- 第一階段：幾乎全部是 **Chrome N（Windows）**
- 第二階段：主力 UA 切換到 **Chrome N+1（Windows）**

而且郵箱字首模式和 UA 之間存在配套關係：

- 「類人名」「5 位」「7 位」字首 → 基本全對應 Chrome N
- 「6 位隨機串」字首 → Chrome N+1 佔絕對主體

字首切換和 UA 切換是同步發生的。更像是註冊環境整體做了一次升級替換。

## 04 / 和全量使用者一比，差距就暴露了

**但和全量使用者放在一起比，差異就暴露了。**

| 維度 | 可疑域名 | 全量使用者 |
|------|----------|----------|
| Session 結構 | 幾乎全是單 session | 常見多 session |
| 多 IP / 多 UA 切換 | 基本沒有 | 明視訊記憶體在 |
| UA 豐富度 | ~1000+ session / 3 種 | ~4000 session / 190 種 |
| 註冊→首次使用 | **~5 小時** | ~8 分鐘 |
| 有 usage 的比例 | 73.8% | 81.4% |

**環境高度收斂。** 正常使用者群裡換裝置、換瀏覽器是常事——4000 個 session 對應 190 種 UA。而可疑域名這邊，1000+ 個 session 只出現了 3 種 UA，集中度差了兩個數量級。

**先備號，再啟用。** 普通使用者註冊後中位數 8 分鐘就開始用；這批帳號中位數要 5 個小時。不是不用，而是更像"先把號建好，回頭再擇時啟用"。

**部分投入使用。** 73.8% 的帳號最終確實產生了 API 呼叫——這不是純廢號，而是一個有選擇地啟用的帳號池。

## 05 / 不只是刷資料，是真的在消耗資源

如果這些帳號只是註冊了放著，那損失還好。但實際情況是——**它們在大規模呼叫 API**。累計消耗了**數十億 Token**，覆蓋平臺上大部分主流模型，推理成本不是一個小數目。

而且呼叫分佈不是集中在一兩個模型上，而是廣泛地覆蓋了多個模型——從幾千到幾萬次呼叫不等。

這不是「註冊領積分然後走人」。是**系統性地消耗平臺的 API 資源**。

## 06 / 技術覆盤：四個值得帶走的方法論

**🔍 永遠要建基線**

很多指標單看沒意義。"註冊後很快建了 session"聽起來正常——但全站 80% 的使用者都這樣。只有和基線對比，才能區分"正常"和"異常"。

**📊 交叉分析 > 單維度判斷**

單看字首、單看 UA、單看註冊時間，每個都能解釋成"巧合"。但當三個維度同步切換，巧合的機率就趨近於零。

**⏱ 把時間線拉開看**

聚合資料會掩蓋階段性變化。按天甚至按小時拆開，才能看到"試探 → 放量"的切換點。

**🎯 剋制比定性更有說服力**

我們全程沒有說"這是惡意攻擊"。我們只說了資料呈現的模式。剋制的結論反而更有說服力——因為事實本身已經夠清楚了。

## 07 / 結論

這個可疑域名下的 1000+ 個帳號，是一組**高度同質化、批次化、流程化**的帳號群。

- ✅ 存在明顯的"試探 → 放量"兩階段切換
- ✅ 字首模式、UA 指紋、註冊節奏三個維度同步變化
- ✅ 和全量使用者對比，環境收斂度、啟用時間、session 結構均顯著偏離
- ✅ 更像「先建號池、再分批啟用」的模式，而非簡單的垃圾註冊

對早期 SaaS 產品來說，這類批次註冊未必立刻致命。但它的影響是實打實的——**被薅走的 API 成本、被汙染的增長資料、以及放任不管後可能的規模化升級。** 越早建立異常檢測能力，越早止損。

## 08 / 我們把排查方法做成了開源 Skill

上面這套排查流程，我們整理成了一個可以直接用的開源 Skill：**abuse-hunter**。

安裝方式很簡單，在 Nexu 裡輸入：

```
/skill install https://github.com/nexu-io/harness-engineering-guide/tree/main/skills/abuse-hunter
```

裝好後，一句話啟動排查：

```
幫我排查一下最近註冊量異常高的郵箱域名，看看有沒有批次刷號
```

它會自動跑完 **6 步排查**，輸出一份帶評分的報告：

- **郵箱域名聚類** — 找出註冊量異常高的域名
- **註冊節奏分析** — 是自然增長還是批次注入
- **字首模式識別** — 人工建立還是程式生成
- **UA 指紋對比** — 環境多樣性 vs 收斂度
- **啟用時間分析** — 註冊即用還是先備號再啟用
- **積分消耗統計** — 量化實際經濟損失

最終輸出 12 分制綜合評分 + 處置建議。還附帶一個 Python 指令碼，匯出 CSV 也能離線跑。
